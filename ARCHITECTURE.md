# Архитектура

Документ описывает устройство пакета `cardiac_em`: слои, правила
зависимостей, ключевые проектные решения и точки расширения. Читать
перед тем, как добавлять новый код, — он отвечает на вопрос «куда это
положить».

---

## 1. Принципы

**1.1. Зависимости строго однонаправленны.**

```
config → fem → models → solvers → coupling → runtime → control
                                                  ↓
                                                 io
                                                  ↓ (только файлы)
                                              analysis
```

Модуль импортирует только из слоёв левее/выше себя. Обратных импортов
нет. Нарушение этого правила — первое, что нужно искать, когда
непонятно, почему что-то стало трудно менять.

**1.2. Никаких модульных глобальных параметров.**

Всё, что описывает прогон, живёт в объекте `SimulationConfig` и
передаётся явно. Это не про аккуратность: пока параметры лежат в
глобалах модуля, в одном процессе нельзя корректно выполнить две
разные конфигурации — вторая унаследует изменения первой. Именно это
блокировало бы параметрические серии и будущий интерфейс управления.

**1.3. `config/` не зависит от DOLFINx.**

Подпакет конфигурации использует только стандартную библиотеку и numpy.
Следствие: конфигурации серий можно собирать и валидировать в лёгком
окружении, а `analysis/` читает сохранённые конфиги, не таща FEM-стек.
Это проверяемое свойство — не нарушайте его импортом `dolfinx` в
`config/`.

**1.4. `analysis/` не зависит от расчётной части вообще.**

Постобработка читает **файлы результатов**, а не живые объекты солвера.
Поэтому анализ запускается отдельно от расчёта: в ноутбуке, на другой
машине, через недели после прогона.

**1.5. В конфиг идёт то, что физически осмысленно.**

Численные допуски реализации (например, округление координат при
сопоставлении DOF в чекпоинтах) остаются внутренними константами
модулей. Иначе конфиг превращается в свалку всех чисел проекта.

## 3. Двойная сетка

Электрика и механика считаются на **разных сетках одной физической
области**:

* электрической нужен мелкий шаг, чтобы разрешить фронт возбуждения
  (характерная ширина фронта ~0.1–0.3 мм);
* механической мелкий шаг не нужен — поле перемещений гладкое, а
  стоимость нелинейного решения SNES растёт с числом DOF быстрее
  линейного.

### 3.1. Два способа задания

**(а) Вложенные сетки — предпочтительный способ.**

```python
DualMeshConfig.nested(RectangleMeshSpec(nx=80, ny=80), coarsening=4)
# механика получится 20×20
```

Механическая сетка — целочисленное огрубление электрической, поэтому
каждая механическая ячейка точно содержит `k×k` электрических.
Согласованность областей гарантирована построением.

**(б) Две независимые спецификации — общий случай.**

```python
DualMeshConfig(electric=RectangleMeshSpec(nx=80, ny=80),
               mechanical=RectangleMeshSpec(nx=25, ny=25))
```

Понадобится, когда механическая сетка придёт из отдельного файла.
Согласованность областей здесь — **проверяемый инвариант**
(`__post_init__`), а не гарантия.

### 3.2. Почему различие существенно

При вложенности перенос `T_act` с мелкой сетки на крупную — **точное
осреднение** по `k²` ячейкам. Без вложенности приходится брать значение
ближайшей ячейки, и крупная механическая ячейка «видит» одну мелкую
вместо среднего по всем. В момент прохождения фронта, когда `T_act`
внутри крупной ячейки меняется от нуля до пика, это даёт реальную
ошибку в суммарной силе, а не косметическую.

Поэтому `DualMeshConfig.nesting()` возвращает не булево значение, а
структуру `MeshNesting` с коэффициентами `kx, ky` и причиной отказа:
слой `coupling/` по ней выбирает точный оператор, когда тот законно
доступен, и честно сообщает о приближении, когда нет.

### 3.3. Что общего у двух сеток

Области неоднородности (`RegionSpec`) заданы **аналитически по
физическим координатам**, поэтому применяются к каждой сетке
независимо и корректно — переносить карты регионов между сетками не
нужно. Это свойство стоит сохранять: как только регион станет
зависеть от нумерации ячеек, двойная сетка сломается.

## 4. Перенос полей между сетками

Перенос оформляется **именованными каналами**, а не одной функцией
под `T_act`:

| Канал | Направление | Пространства | Оператор |
|---|---|---|---|
| `T_act` | Э → М | DG0 → DG0 (или квадратурные точки) | осреднение по ячейке (вложенные) / ближайшая ячейка (общий случай) / native nonmatching |
| `lambda_f` | М → Э | DG0 → P1 | интерполяция P1 *(планируется, МЭОС)* |
| `dlambda_f/dt` | М → Э | DG0 → P1 | интерполяция P1 *(планируется, МЭОС)* |

Два соображения, которые архитектура не должна закрывать:

1. **Обратные каналы** понадобятся при переходе к механоэлектрической
   обратной связи (растяжение-активируемые токи, деформационно-зависимая
   диффузия). Направление М→Э — крупная→мелкая, там кусочно-постоянная
   инъекция хуже линейной интерполяции. То есть нужны операторы **разных
   типов**, а не один универсальный.
2. **Цель переноса `T_act` не обязана быть ячейками DG0 механики.**
   Более точный вариант — интерполяция прямо в квадратурные точки
   механической формы. Это параметр канала, а не вшитое решение.

Обе сетки статичны в референсной конфигурации, поэтому отображение
между ними строится **один раз** при старте и переиспользуется каждый
механический шаг.

## 5. Конфигурация

`SimulationConfig` — единственный объект, нужный расчётному ядру:

```python
@dataclass
class SimulationConfig:
    mesh:        DualMeshConfig
    tissue_base: TissueBaseParams
    regions:     list[RegionSpec]
    stimulus:    StimulusProtocol
    time:        TimeStepping
    preload:     PreloadProtocol
    output:      OutputConfig
    restart:     RestartConfig
```

### 5.1. Валидация в три уровня

* **Ошибки внутри группы** — `__post_init__` каждого dataclass:
  отрицательная диффузия, нулевой радиус области, перекрывающиеся окна
  стимулов, опечатка в ключе переопределения.
* **Ошибки между группами** — `SimulationConfig.check()` поднимает
  исключения на несовместимых сочетаниях.
* **Предупреждения** — `check()` возвращает список подозрительного, но
  законного: сетки перепутаны местами, стимул позже конца счёта,
  стимульная зона уже двух ячеек, сетки не вложены.

Смысл разделения: неверная конфигурация должна падать до запуска
счёта, а не портить результат на десятой минуте.

### 5.2. Сериализация и её граница

`to_dict()`/`from_dict()` дают JSON-совместимое представление. Оно
попадает в манифест прогона и в чекпоинт — благодаря этому рестарт
восстанавливает в том числе неоднородность ткани.

Исключение — `CustomRegion` с произвольным Python-предикатом: он не
сериализуется. `to_dict()` на такой конфигурации **поднимает ошибку**,
чтобы потеря неоднородности не прошла незаметно;
`to_dict(skip_unserializable=True)` пропускает её по явному согласию.

### 5.3. Плоские ключи переопределений

Переопределения областей задаются плоским словарём: `"AP_c1"`,
`"D_LONG"`, `"T_MAX"`, `"MU"`. Имена совпадают с историческим форматом
JSON-файлов областей, поэтому старые файлы читаются без правки.
Соответствие плоских ключей и полей dataclass — в `FLAT_KEYS` каждой
группы параметров.

Ключи **валидируются**: опечатка вроде `"AP_C1"` раньше молча ничего не
делала (и «ишемическая зона» оказывалась здоровой), теперь это ошибка.

## 6. Ход счёта: расписание событий и наблюдатели

Основной цикл разложен на две независимые части.

**Расписание** (`runtime/schedule.py`) выдаёт последовательность `Tick`:
на каждом электрическом шаге — решать ли механику, писать ли поля,
сохранять ли чекпоинт, какие снимки сюда попадают. Нумерация
механических шагов глобальная (от t = 0), поэтому при продолжении с
чекпоинта моменты записи не сдвигаются.

**Наблюдатель** (`runtime/observers.py`) — класс с методами
`on_preload_step`, `on_preload_done`, `on_start`, `on_mech_tick`,
`on_finish`, `on_abort`. Консольная печать, запись полей, ряды,
чекпоинты и манифест — всё это наблюдатели; расчётный цикл о файлах не
знает. Наблюдатели вызываются на всех рангах MPI (диагностика
коллективная); в `on_abort` коллективные операции запрещены.

Это шов для будущего управления: наблюдатель, пишущий прогресс в
статус-файл, даёт интерфейсу возможность следить за счётом, ничего не
зная о солвере; расписание событий — естественное место для «остановиться
здесь» и «сменить протокол на ходу».

## 7. Манифест — контракт для анализа

Каждый прогон пишет `run.json` (`io/manifest.py`):

* сериализованный `SimulationConfig`, включая имена моделей клетки и
  материала;
* спецификации и размеры обеих сеток, расписание, перенос T_act;
* откуда взято состояние при продолжении;
* предупреждения; список выходных файлов;
* версии кода и библиотек, git-коммит, время счёта, статус
  (`running` → `finished` / `failed`). Во время счёта файл обновляется
  прогрессом — это и статус-файл для внешнего наблюдения.

Рядом: `series.csv` (диагностика на каждом механическом шаге),
`snapshots/*.npz` (поля с координатами, упорядоченные по (y, x) — для
анализа без DOLFINx), XDMF — для ParaView.

`analysis/` читает **манифест, а не захардкоженные пути**. Следствие:
постобработка работает офлайн, в другом процессе, без DOLFINx —
достаточно numpy/pandas.

Карты времён активации и реполяризации пишет `io/activation.py` с
разрешением электрического шага (событие `on_electric_step`, моменты
уточняются интерполяцией) — снимков раз в миллисекунду для скорости
проведения мало. `analysis/biomarkers.py`: сводка активации, скорость
проведения (наклон и локальное поле), APD по регионам, блок проведения,
реституция, механические пики и интегралы. Анализ не импортирует ни
одного расчётного слоя, включая `io` (проверяется тестом архитектуры).

## 8. Чекпоинты

Состояние сохраняется как пары **(координата → значение)**, а не
сырые массивы DOF. Такое представление инвариантно к числу MPI-рангов
и к внутренней нумерации DOF в DOLFINx: чекпоинт, снятый на одном
ядре, корректно читается прогоном на восьми, и наоборот.

Это же свойство делает чекпоинты **инвариантными к тому, на какой из
двух сеток живёт поле** — сопоставление идёт по физическим координатам.

При несовпадении сеток восстановление по умолчанию — **ошибка**;
перенос по ближайшему соседу включается явным
`RestartConfig(allow_interp=True)`, чтобы «почти правильный» результат
не получался молча. Размеры области и модель клетки обязаны совпадать
всегда. Расхождения физических параметров с прогоном-источником
перечисляются в предупреждениях поимённо.

Реализация — `io/checkpoint.py`. Хранится полное состояние клеток и
перемещения; T_act пересчитывается из состояния. Запись атомарная.
`ckpt_preloaded.npz` пишется сразу после преднагрузки — общая стартовая
точка для серий. Чекпоинты монолитной версии читаются (с поправкой
времени на один шаг — там записывалось начало шага).

## 9. Точки расширения

| Хочу добавить | Правлю только |
|---|---|
| новую модель клетки | `models/cell/<name>.py` + регистрация в реестре |
| новую форму области | `config/tissue_spec.py` — один класс с `contains()` и `to_dict()` |
| геометрию из файла (.msh) | `FileMeshSpec` в `config/mesh_spec.py` + ветка в `fem/mesh.py` |
| другой оператор переноса | `coupling/transfer.py` — одна стратегия |
| новую функцию энергии | `models/passive/<name>.py` |
| новый биомаркер | `analysis/biomarkers.py` — расчётный код не трогается вообще |
| запуск серии прогонов | `control/sweep.py` — `runtime/` не трогается |
| другой формат вывода | `io/fields.py` |

## 10. Состояние и нерешённые вопросы

Реализованы шаги 1–10 (см. таблицу в README).

Решения, которые нужно принять до соответствующих шагов:

1. **Перенос `T_act`** (шаг 4): осреднение по ячейке или интерполяция в
   квадратурные точки механики? Второе точнее и дороже, влияет на
   сигнатуру канала.
2. **Обратные каналы МЭОС** (шаг 4): закладывать сразу пустыми или
   отложить до растяжение-активируемых токов?
3. **Формат хранения полей** (шаг 9) — РЕШЕНО: XDMF для просмотра и
   `.npz` с координатами для анализа и чекпоинтов, без новых
   зависимостей. На масштабе 1–5 тыс. узлов сбор на нулевой ранг
   дешёв. К HDF5/`adios4dolfinx` стоит вернуться при переходе к
   сеткам в сотни тысяч узлов: тогда сбор на один ранг станет узким
   местом. Формат чекпоинта версионирован (`version` в файле).
4. **Параметры модели клетки** (шаг 5): сейчас `ReactionParams` лежит в
   `config/tissue_spec.py` как параметры конкретной двухпеременной
   модели. С появлением абстракции `CellModel` они переедут в
   `CellModelSpec`, а в `tissue_spec.py` останется только то, что
   относится к ткани как к среде.
